## 1. 当前功能现状

### 1.1 服务边界

| 项 | 值 |
|---|---|
| 服务名 | `sports-takeout-ai` |
| 角色 | Spring Boot 主后端旁挂的独立 AI 微服务，**只读** sports_takeout 库 |
| 端口 | `18000`（dev 默认） |
| HTTP 框架 | FastAPI 0.115.6 + Uvicorn 0.32.1 |
| 对外接口 | 1 个业务接口 + 1 个健康检查 |
| 部署形态 | 单进程、单实例、无容器化（docker-compose 未包含 ai-service） |

**当前对外接口清单：**

| Method | Path | 说明 |
|---|---|---|
| GET | `/healthz` | 健康检查，返回 env / mock_mode / llm_model |
| POST | `/ai/recommend-coach` | 教练智能推荐，自然语言 → Top N 教练 + 理由 |

### 1.2 已实现 Agent：教练推荐（recommend_coach）

**拓扑（固定 3 节点串行 DAG，无循环、无分支）：**

```
START
  │
  ▼
┌─────────────────────┐
│ Node 1              │  LLM 节点
│ extract_intent      │  用户自然语言 → IntentExtraction 结构化 JSON
│ (LLM 抽取)          │  失败 → 关键词正则 mock 兜底
└─────────────────────┘
  │
  ▼
┌─────────────────────┐
│ Node 2              │  纯规则节点（无 LLM）
│ retrieve_and_rank   │  MySQL 查 coach/course/schedule → 5 维加权打分
│ (SQL + 规则打分)    │  Top N 候选 + 匹配课程 + 预算过滤
└─────────────────────┘
  │
  ▼
┌─────────────────────┐
│ Node 3              │  LLM 节点
│ generate_reason     │  候选 + 用户目标 → 2~3 句推荐理由
│ (LLM 生成理由)      │  失败 → mock 模板兜底
└─────────────────────┘
  │
  ▼
 END
```

**输入契约：**

```json
POST /ai/recommend-coach
{
  "user_query": "望京，预算 200 以内，想产后恢复，周末上午",
  "city_code_override": null,   // 可选：小程序已知城市时覆盖 LLM
  "top_n": 3                     // 1~5
}
```

**输出契约（[RecommendResult](../app/schemas/coach_recommend.py)）：**

```json
{
  "user_query": "...",
  "intent": { /* IntentExtraction：city/district/specialization/tags/level/price/slot... */ },
  "candidates": [ /* Top N CoachCandidate：含 5 维子打分 + 综合分 */ ],
  "coach_ids": [1, 3, 2],
  "recommend_reason": "针对你的目标「产后恢复」，推荐先约张教练、李教练...",
  "matched_course_name": "上门产后恢复私教课",
  "matched_course_price": 199.0,
  "over_budget": false,
  "used_mock": false
}
```

**设计要点：**
- Node 2 不调 LLM，纯 SQL + 5 维加权（评分 40% / 语义匹配 35% / 等级 10% / 距离 10% / 档期 5%）——比让 LLM 在数百教练里选 Top3 更准、更便宜
- 全程 Pydantic 强类型 + `normalize_for_pydantic` 适配层（应对 LLM 字段名漂移）
- 三层 mock 兜底：`AI_MOCK=1` 或无 API Key 时全链路跑假数据，离线可演示

### 1.3 基础设施层

| 模块 | 文件 | 现状 |

## 2. 商业化目标下的差距分析

商业化项目对 AI 微服务的硬性要求：**并发扛得住、故障不雪崩、工程能协作**。当前差距按这三维度展开。

### 2.1 并发维度

| 项 | 现状 | 商业化要求 | 差距 |
|---|---|---|---|
| API 入口 | `def recommend_coach(...)` 同步函数 | `async def` | 同步函数会阻塞 FastAPI event loop，每个请求占用一个 worker 线程 |
| Graph 执行 | `RECOMMEND_GRAPH.invoke(...)` 同步 | `ainvoke` | LangGraph 已支持 async，未利用 |
| LLM 调用 | `litellm.completion(...)` 同步 | `acompletion` | `clients/llm.py` 已有 `achat` 但节点未用 |
| MySQL 连接池 | 默认 5 个连接 | 业务峰值 ≥50 并发需 20~50 连接 | `pool_size` / `max_overflow` 未显式配置 |
| Redis 缓存 | 配置已读，**代码未使用** | 高频相同 query 应缓存 24h | 无 `@cache` 装饰器，相同 query 每次都打 LLM |
| 限流 | 无 | 每用户/IP 限流，防恶意刷 | 无中间件，无 Redis token bucket |
| 异步任务队列 | 无 | 长耗时操作（如批量推荐）应入队 | 无 Celery / RQ / arq |

### 2.2 高可用维度

| 项 | 现状 | 商业化要求 | 差距 |
|---|---|---|---|
| 部署形态 | 本地 `python -m app.main` | 容器化 + 多副本 | docker-compose.yml 未包含 ai-service；无 Dockerfile |
| 健康探针 | `/healthz` 浅探活 | readiness（含 DB/LLM 探活）+ liveness 分离 | 现有 healthz 不查依赖 |
| 优雅停机 | 无 | SIGTERM → 拒新请求 → 等待在飞 → 退出 | lifespan 只 log |
| 熔断降级 | 无 | LLM/DB 连续失败应熔断走 mock | 节点级 fallback 是有的，但无全局熔断器 |
| 重试策略 | LiteLLM 内部 2 次重试 | 业务级重试 + 退避 + 不同节点不同策略 | 失败立即 fallback，无退避重试 |
| 超时控制 | LLM 单次 60s | 分层超时（HTTP 5s / LLM 30s / DB 3s） | DB 无显式超时 |
| 错误码体系 | HTTPException 通用 500/400 | 错误码 + 错误分类（限流/降级/上游失败） | 无业务错误码 |
| 监控告警 | 无 | QPS / latency p99 / 错误率 / LLM token 用量 | 无 metrics 端点 |

### 2.3 工程化结构维度

| 项 | 现状 | 商业化要求 | 差距 |
|---|---|---|---|
| 目录分层 | app/{clients,graphs,schemas} | + api/（路由层）+ services/（业务编排）+ middleware/ + core/（异常/日志） | 当前 main.py 既当路由又当编排，100+ 行混在一起 |
| 配置分层 | 单 .env + dev/test/prod 字段 | dev/test/staging/prod 多文件 + secret 管理 | 仅一个 .env.example |
| 日志 | logging.basicConfig | 结构化 JSON 日志（loguru/structlog）+ trace_id 贯穿 | 纯文本，无 request_id |
| 异常处理 | try/except + HTTPException | 全局异常中间件 + 错误码 + 不泄露内部栈 | main.py 内 try/except 重复 |
| CI/CD | 无 | GitHub Actions：lint + test + build + push image | - |
| 容器化 | 无 Dockerfile | 多阶段构建 + 健康探针 + 非 root 用户 | sky-server/admin-web 都有，独 ai-service 漏了 |
| API 文档 | FastAPI 默认 OpenAPI | 标签分组 + 请求/响应示例 + 错误码表 | 当前只有默认生成的 |
| 版本管理 | 0.1.0 硬编码 | API 版本前缀 `/v1/ai/...` + 语义化版本 | 无版本前缀，未来破坏性变更没退路 |
| 测试覆盖 | 1 个 smoke test | 单测 + 集成 + 契约测试 + Eval 集回归 | 严重不足 |
| 依赖锁定 | pyproject.toml 锁主版本 | poetry.lock / uv.lock 锁传递依赖 | 无 lock 文件 |

## 3. 三大工程缺口（Agent 维度专项）

> 这一节聚焦 Agent 自身的能力缺口，区别于 §2 的工程基础设施差距。

### 3.1 Harness 工程（Agent 脚手架 / Eval / 可观测）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 离线测试 | 1 个 smoke test，4 条 query，只断言结构合法性 | 无 Eval 数据集（query → 期望 intent / coach_ids 标注）；无 metric |
| 评估指标 | 无 | 缺：IntentExtraction 字段准确率、Top-K 命中率（标注教练是否在 Top3）、推荐理由可读性、平均 token / 平均 latency |
| Trace 可观测 | 无 | 未接 LangSmith / Langfuse / Phoenix，节点级 token / latency / 失败率看不见 |
| Prompt 管理 | `SYSTEM_NODE1` / `SYSTEM_NODE3` 硬编码常量 | 无版本化、无 A/B、无 few-shot 池、改 prompt 无回归保护 |
| 反馈回流 | `used_mock` 仅本地调试 | 小程序用户点击/评分未回流成 Eval 集，无法持续优化 |
| 重试包装 | 仅 Node3 LLM 失败回退 mock | Node1 抽 JSON 失败应重试 N 次再 fallback |

### 3.2 Loop 工程（Agent 循环）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 条件分支 | `base.py` 写了 `ConditionalRouter` 但未用 | Node2 候选为空 → 应回 Node1 放宽条件重抽（refine loop） |
| 重试循环 | 无 | Node1 LLM 抽 JSON 失败 → 累加修正提示重试 N 次 |
| ReAct / Tool Loop | 无（节点写死 SQL，非 LLM 自主调工具） | 证书审核 Agent 需要 LLM 自主调用「OCR 工具 / 查库工具 / 比对工具」循环 |
| HITL 人工介入 | 无 | 证书审核最终判定需 LangGraph `interrupt` + Checkpointer 暂停等管理员确认 |
| 自我反思 | 无 | Node3 推荐理由过长/不含数据时应回 Node3 重写 |

### 3.3 MCP 功能（Model Context Protocol）

完全缺失。当前所有数据访问都直接 `import` [clients/db.py](../app/clients/db.py) 的 `fetch_all`，工具与节点紧耦合。

| 项 | 现状 | 需要配置 |
|---|---|---|
| MCP Server | 无 | 把 `_fetch_coaches / _fetch_courses / _fetch_available_slots` 抽成 MCP tool |
| MCP Client | 无 | LangGraph 节点改走 MCP client 调用工具，为多 Agent 共享工具铺路 |
| 跨语言工具复用 | 无 | Spring Boot 端把「下单/接单/状态流转/派单池查询」暴露成 MCP tool 给 AI 调用 |
| 配置项 | `.env.example` 无 MCP 字段 | 加 `MCP_TRANSPORT` / `MCP_SERVER_URL` / `MCP_TIMEOUT` |
| 依赖 | `pyproject.toml` 无 mcp SDK | 加 `mcp` 包 |

## 4. 路线图（建议执行顺序）

按「**ROI 高 + 解锁后续工作**」原则排序，每阶段都能独立交付、独立验收。

### Phase 1（建议起手）· Loop 工程基础 → 文档 #02

**为什么先做：**
- 改动局部、风险低（不动对外契约）
- 立刻提升推荐稳定性（Node2 空结果不再硬塞 mock 教练）
- 给后续两个新 Agent 打通 HITL / ReAct 的工程基础

**交付物：**
- `recommend_coach` 接 `ConditionalRouter`（Node2 空结果 → 回 Node1 放宽条件）
- Node1 LLM 抽取失败重试循环（带修正提示累加）
- Node3 推荐理由质量门控（过长/无数据 → 回 Node3 重写）
- 引入 `MemorySaver` Checkpointer 为 HITL 铺路

### Phase 2 · 商业化加固（并发/高可用/工程化） → 文档 #03

**为什么排第二：**
- 没有这层底座，Phase 4 的 Eval 跑不出可信数据（无 trace 看不到瓶颈）
- 没有容器化，Phase 5 的 MCP 多副本部署不起来

**交付物：**
- 全链路异步化（async def + ainvoke + acompletion）
- MySQL 连接池参数化 + Redis 缓存层
- Dockerfile + 加入 docker-compose
- 结构化日志 + request_id + 全局异常中间件
- `/readyz` 与 `/healthz` 分离
- 限流中间件 + LLM 熔断器

### Phase 3 · Harness 工程 → 文档 #04

**交付物：**
- 20 条标注 Eval 集（query → 期望 intent + 期望 coach_ids 子集）
- 3 个 metric 脚本（Intent 准确率 / Top-K 命中率 / 理由可读性）
- Langfuse 自部署接入
- Prompt 抽到独立配置文件 + 版本化

### Phase 4 · MCP 工具层 → 文档 #05

**交付物：**
- Python 侧 MCP Server（暴露 coach/course/schedule 查询工具）
- LangGraph 节点改走 MCP client
- Spring Boot 端 MCP Server（暴露订单/派单工具）
- 跨语言工具注册中心

### Phase 5 · 第二、第三个 Agent → 文档 #06

**交付物：**
- 评价摘要 Agent（批量给历史评价打标签 + 总结优缺点）
- 证书审核 Agent（OCR + 国职库比对 + HITL 管理员确认）
